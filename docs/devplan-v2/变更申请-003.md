## 2. 精确公共类型与签名

以下是M1完整新增类型及LedgerCheckpoint增量；其余字段及顺序按01保留。所有字段显式必填，Mapping防御性复制为不可变对象。

```python
@dataclass(frozen=True)
class ValuationMark:
    contract_id: str
    price: Decimal | None
    as_of_nano: int | None
    valued_at_nano: int | None
    source_bar_id: str | None
    source_bar_sha256: str | None
    rule_id: str | None
    status: Literal["CURRENT", "STALE", "UNVALUED"]
    reasons: tuple[str, ...]

# LedgerCheckpoint新增字段，分别位于account、pending_intents、processed_event_ids之后：
valuation_marks: tuple[ValuationMark, ...]
pending_remaining_lots: Mapping[str, int]
processed_fill_hashes: Mapping[str, str]

# M4 ContinuousLedger中的修订声明：
def apply_fill(self, fill: Fill, rule: TradingRule) -> bool: ...
def mark(self, bars: Mapping[str, MarketBar | None], as_of_nano: int,
         trading_day: date, rules: tuple[TradingRule, ...]) -> AccountSnapshot: ...
def checkpoint(self, states: tuple[StrategyState, ...],
               pending_intents: tuple[OrderIntent, ...],
               model_hashes: Mapping[str, str],
               qualification_hashes: Mapping[str, str], *,
               pending_remaining_lots: Mapping[str, int]) -> LedgerCheckpoint: ...
```

apply_fill由None改为bool：True=首次入账，False=同内容重复且无副作用。mark由无来源prices改为完整已用bars；checkpoint只增加必填关键字参数。restore、snapshot、record_event、M3B apply_execution、run_decision_replay及run_shadow签名保持不变。新账本只能从无历史成交/持仓的合法初始账户开始，已有账户必须提供checkpoint，不能从非空AccountSnapshot猜恢复事实。

## 3. 估值、缺失与PIT

1. valuation_marks按contract_id排序且唯一，集合恰为account.lots中的持仓合约；首次持仓尚未完成估值也必须有UNVALUED记录。最后批次平完才移除mark，历史已消费规则及Fill hash继续保存。
2. CURRENT/STALE的六个nullable事实字段必须全部非空。price是正有限Decimal；as_of_nano=实际使用bar.end_nano，valued_at_nano=该价格/规则组合最后成功使用的事件时点，满足`as_of<=valued_at<=account.as_of`。bar必须完整、有效，且`end<=available_at<=valued_at`并通过原时效政策；规则在valued_at有效/可见，乘数及所持方向保证金率已知。完整bar规范hash绑定已消费证据，rule_id通过checkpoint.rule_hashes绑定完整TradingRule，无需重复存rule hash。已可见但缺字段、实际参与检查的规则仍留内容hash；完全不存在/不可见的规则不造hash。CURRENT不提升原SCENARIO等证据等级。
3. 应有价缺键/None、过期或当前估值规则不可用时，保留旧价格、两个时间、bar证据及rule_id，仅把状态改为STALE；reasons是去重排序的PRICE_MISSING/PRICE_STALE/RULE_MISSING非空子集，CURRENT为空。陈旧估值以旧组合计算当前剩余真实lots，数量不变时贡献完全不变；新成交造成的数量变化不能被旧汇总覆盖。原120秒等时效门槛不变，旧bar重发不能刷新价龄或解除仍成立的缺失状态。
4. 从未形成完整组合时status=UNVALUED，六个事实字段全部None，reasons说明缺价/缺规则。不能把成交价、入场价、0或未来价格当第一笔mark；age及该合约损益/保证金贡献为未知。账户Decimal字段只累计已知贡献，equity=cash+已知unrealized，day_net保持原恒等式；明确标MISSING/INCOMPLETE，不能将该小计当完整NAV、零未知负债或准入预算。最后可靠峰值/日初基数与熔断保留；已有INVALID原因不被覆盖。
5. 有陈旧组合则账户至少STALE、reconcile=INCOMPLETE；有UNVALUED则MISSING/INCOMPLETE，差额小计0也不能PASS。OPEN/ADD阻断，REDUCE/EXIT仍走原风险与可成交规则，不能借未知费用制造完成平仓。价龄唯一为`account.as_of_nano-mark.as_of_nano`纳秒，UNVALUED为None，不另存可漂移的age缓存。
6. restore只校验/加载checkpoint及实际已消费依赖；不接bars、不重估、不调用apply_fill、不给新sequence/时钟。首次同账户时点snapshot逐字节相同，reconcile结果也相同。原事件缺规则已记录为缺失，可以原样恢复；恢复输入遗失或篡改checkpoint.rule_hashes引用的旧规则必须拒绝，即使另有未来替代规则。

## 4. Fill、pending与提交边界

`processed_fill_hashes[fill.fill_id] = SHA256(canonical_json_bytes(encode_record(fill)))`，包含Fill全部字段及fill_id；规范编码沿用M1 UTF-8/键排序/紧凑JSON/尾LF/Decimal字符串规则。同ID同规范内容只入账一次；同ID异内容报ValueError（允许M4本地子类），整事件候选状态丢弃，不扣费、不占容量、不更新层/pending或检查点。先检查整批原始fills与历史hash及批内重复，再判断event是否已提交，禁止按ID提前吞异常payload。未见新Fill挂于已提交event也拒绝。

M4向M3B传`ExecutionResult(intent_id, new_fills, remaining_lots, status, reasons)`及本次入账后的账户，new_fills只含本事件首次入账的Fill。原始ExecutionResult可以是累计fills，原文保留在日志，不能覆盖成过滤后记录。同一intent的后续PARTIAL有新fill_id必须推进；无新Fill的首次终态/阻断按事件处理一次，已提交事件重播不再推进策略。processed_event_ids只记稳定事件ID，Fill内容与pending量不藏入任何ID字符串。

pending_intents保存原始OrderIntent不改delta_lots。pending_remaining_lots键集恰等于这些intent_id及全部states.pending_intent_ids的并集，每个intent只归属一个strategy/contract/episode匹配的state；值为非零有符号int（非bool），与delta_lots同号且不超过原量。选中时取delta_lots，随后`remaining_after=remaining_before-Σ(new_fill.side*new_fill.lots)`，与回执remaining_lots精确相等。PARTIAL/BLOCKED保留pending；FILLED要求0；EXPIRED/CANCELLED移除活跃pending但原回执保留未成交量。部分层、首次成交收紧退出、全未成交取消及预留释放仍按M3B原规则同步持久化。

账户、marks、Fill索引、M3B返回状态、原挂单/剩余量、容量/资源和事件游标必须属于同一候选事务。全部验证后先发布引用记录并fsync，再原子发布checkpoint，M5最后提交shadow_events行；提交前断写回到上一已提交checkpoint，孤立新checkpoint也不算提交，尾字节只读留证。提交后重复Fill命中hash，费用/层/容量不重复。M4纯离线发布仍需完整manifest，M5沿用既有分段链，不新增旁路账本。

恢复前，M4/M5在当前段及祖先已提交前缀验证：所有已入账Fill与processed_fill_hashes一一对应（含已平仓历史），同ID原Fill内容相同；原OrderIntent、原ExecutionResult及规则引用可读取，账户/批次与成交日志守恒。fills产物仅首次入账写实体，重播引用旧实体；源mark的单bar证据从原冻结输入或已提交BAR记录核对。影子bar按M5既有原FeedEvent及独立接收/验证时间还原当时真正消费的MarketBar及受控available_at，hash绑定此完整对象，原事件不改。原始日志用于验证引用，不用于弥补旧checkpoint缺字段或重新扣费；缺已提交实体即FAILED。

**04原维护者的精确修订建议（本次不写04）：**将§7的“apply_execution先按event_id/intent_id幂等验证再推进；重复反馈不重复计层”替换为“宿主M4按事件提交及完整Fill内容去重，只把本次新Fill和最新remaining/status交apply_execution；同一仍pending的intent可多次PARTIAL，不能按intent_id整轮短路；M3B核验归属并推进一次，宿主将结果与Fill索引/pending原子保存”。其余未知intent/合约/episode拒绝规则保留。StrategyState现有层/退出/pending字段足够，**不需新增StrategyState字段或修改apply_execution签名**；新增的通用挂单剩余量由M1/M4负责。04措辞订正由原维护者在主会话授权范围落实，首锁前须对齐，不以本申请授权越界编辑。
