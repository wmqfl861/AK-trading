# J7 合同锁分级与集中冻结变更申请

**状态：PROPOSED / NOT_IMPLEMENTED。** 作者：Codex Astra/max。日期：2026-11-13。依据：[DECISIONS J7](repo-audit-20261113-claude/DECISIONS.md)、[NEXT-BATCH 的 J7](repo-audit-20261113-claude/NEXT-BATCH.md)、[REVIEW Y11](repo-audit-20261113-claude/REVIEW.md)。源码核对基点：`0e4394b41babec2c0d9fc8e1dbc81e442e5f9ee2`。

本批只交付本申请，实施排在 K40 之后，并由后续有效实施计划确定写集、入口和兼容版本。**本文不成为当前工程运行的放行依据。K12 本批仍按现行“新泛型 F → 独立源码／输入报告 R → 新完整合同锁 → 实际 verify”流程执行。** 没有生成新锁、改变现行规则或启动下一批。

## 1. 问题与目标

现行 [artifacts.py](../src/ak_trading/v2/artifacts.py) 的 `build_contract_lock` 同时绑定源码、签名、schema、夹具 F、测试／检查名单、policy 和独立报告哈希。`validation/experiments.py` 的 `_execute_validation` 等入口要求完整锁，源码变化因此可能让一次 profile 也等待新的 F、报告与锁。r6 已修复两种清单抢占同一路径的问题；本申请不撤销这项修复。

Y11 还列出分年工具、`risk_semantics.py`、旧 T7、prepare 脚本及泛型 F 中分散的哈希：其中有来源身份，有历史验收期待，也有“只有这些实现经过语义认可”的限制。把这些含义混在一起，会使普通源码变化直到运行时才暴露为阻塞。

建议将**工程身份校验**与**正式成果接受**分开，同时集中计算和登记冻结身份。工程作业仍须核验自己的确切源码和输入；发布要求保留独立审核。任何锁都不代替作业授权、测试结果或交易许可。

## 2. 两类锁的拟议契约

下表中的 E、P、R 是本申请的对象简称，尚无对应实现或新 schema。

| 对象 | 必须绑定与验证 | 不授予的能力 |
| --- | --- | --- |
| 工程锁 E | 有版本的明确锁类型；完整声明源码／测试文件的相对路径、原始 bytes/SHA；真实夹具及输入清单闭包；声明的测试 nodeid／检查名单。保留现行签名、schema、policy、required checks 校验，作为上述源码和名单的派生约束。 | 不含独立报告依赖，不证明测试通过，不签发 readiness、资格或正式研究结论。 |
| 发布锁 P | 明确的另一锁类型和版本；完整 E 的内容身份；独立验收报告 R 的内容身份及审核范围。验证 E 全部约束，再验证 R 对同一 E、证据、验收项、无条件 PASS 和审核独立性的对应。 | 不能以报告文本的 PASS 字样代替证据复算，不能扩大 R 的实际范围，不能授权真实交易或最终 holdout。 |

工程锁只有源码、夹具和测试名单三类绑定来源；既有运行环境、模型／数据身份、注册范围等信息继续由原有运行记录和前置校验承担，不能因拆锁而删除。E 的测试名单是运行与验收范围的声明，实际选择和结果另行记录；不能把更小的 CI 集合登记成完整回归。

E 在未变的源／输入／名单上可复用；任何被绑定字节变化须创建新 E，不能修改旧 E。P 只适用于其确切 E 和 R；源码变化不能继续使用旧 P。锁内不纳入自己的 hash、未来日志、未来输出或尚未完成的报告。缺文件、路径逃逸、可写别名、内容漂移、未知类型／版本均拒绝，不以“工程用途”放过身份不一致。

## 3. 入口与成果边界

| 入口／用途 | 将来拟允许的锁与限制 |
| --- | --- |
| 原本无锁的普通单元测试、静态检查、只读查看既有报告 | 保持原合同，不为每次测试新增造锁或审核要求。 |
| 明确登记的离线 profile、SYNTHETIC 工程回放／冷链演练 | E 可满足锁前置；仍限该作业已有授权、已声明输入及原有验证条件。工程结果必须保存用途与 E 身份。 |
| 新的正式 v2 报告、正式验收证据提交、策略资格认定 | P；同时保留统计／经济／范围完整性和独立复算要求，工程结果不能仅改用途字段就升级。 |
| 消费已认定资格的 shadow／其他现有入口 | 继续验证资格所引用的发布证据链；采用 E 不能绕开 `verify_qualification_evidence`。运行身份与已有资格身份按各自合同交叉核验。 |
| final-holdout、真实交易及真实报撤单 | 锁不提供额外授权。既有用户明确授权、一次性 holdout、执行审核和部署／模拟验收边界全部保留。 |

工程用途必须由入口的明确契约和持久化运行记录共同限定；不能把 `_execute_validation` 的现有 `smoke` 名称直接等同于工程用途，也不能给正式入口加一个可绕过 P 的 `--engineering` 开关。未明确分类的旧入口保持原完整锁要求，禁止静默降级。工程输出可供诊断，正式报告／资格消费者必须明确拒绝其充当已接受证据；后续正式接受需要对应范围的真实独立验证。

拆锁不改变交易默认值、准入条件、费用／保证金／风控参数、统计门槛、窗口长度、留出边界或 `synthetic=false` 的 VERIFIED 日历要求。它不授权新的 H5/H5′、研究、profile、采集或服务操作。

## 4. 集中冻结与无循环证据链

**建议一个冻结脚本集中生成新版本身份清单，复用现有生产函数。** 在 [prepare_t7_contract_inputs.py](../scripts/prepare_t7_contract_inputs.py) 的固定命名空间、真实输入校验、路径保护及 [artifacts.py](../src/ak_trading/v2/artifacts.py) 的校验逻辑上组织生成流程；不在每个模块另存一组手写 hash，也不另建调度器、状态系统或预算系统。脚本名及新 API/schema 名在实施计划中固定，本文不声称它们已存在。

证据依赖保持单向：

```text
冻结源码 S + 原始输入 I + 测试名单 T → 工程锁 E
E + 已终态的测试／复算证据 → 独立验收报告 R
E + R → 发布锁 P
P + 对应运行与资格证据 → 正式成果／资格记录
```

R 绑定被审 E，不绑定未来 P；正式成果可以引用 P。现有报告中的 `contract_lock_sha256` 若承担不同角色，迁移时必须使用显式新 schema 区分 E/P，不能悄悄重释旧字段或制造 `P → R → P` 循环。`verify_contract_lock_with_report` 当前只完成完整锁校验和报告字节绑定；报告侧逐文件 pins、证据绑定和语义复算仍是独立审核者责任，未来也不得省略。

冻结脚本承担以下有限职责：核对既有输入预期；从允许的明确清单计算当前 bytes/SHA；输出与上一版本的逐项差异；完整序列化并验证后，在新目录原子发布。旧源码副本、清单、报告、锁和失败一律保留，不提供覆盖旧冻结件或自动修正不匹配的 force 路径。源码在运行前冻结，stdout/stderr、子进程结果及证据只在生产者终态后封存；排除脚本自身活动输出和未结束的父 CLI 日志。统一生成不读取凭据、运行秘密或整目录中未声明的文件。

Y11 的各类 pin 按含义迁移：

- **当前版本的来源身份**：集中写入 E 的来源表及差异表，消费者使用同一份冻结身份。
- **历史验收期待**（包括旧 T7）及**原始输入来源 pins**（包括 prepare 的五个固定输入）：保持原件和期待；生成器先校验它们，不能用“当前读到的 hash”替换期待来通过。
- **语义认可名单**（例如 `risk_semantics.py` 的已知实现）及**必需计划依赖**：可以集中记录其来源和批准范围，但自动计算 hash 不会产生语义认可或补齐缺失计划。新的认可版本需要实际评阅；缺失或未知仍报告具体阻塞。

因此可以统一生成和核验工具，不能把所有 pin 统一成“每次读取后自动更新”。旧 T7 重冻仍属于 J18 的另行实施范围。

## 5. 兼容与迁移建议

保留现行完整锁的 schema、验证器和历史 bytes，旧锁只在其原源码／夹具／报告上有效。新 E/P 使用明确类型及独立 schema 版本；旧消费者不能把缺少报告字段的对象默认当 E，也不能把旧完整锁直接改名当 P。旧结果的核验继续走旧协议，不追溯要求重跑已接受研究。

未来实现应集中在 `artifacts.py` 的构建／验证边界及声明的工程入口；`validation/experiments.py`、`validation/shadow.py` 和 `verify_qualification_evidence` 的调用需按入口分类显式迁移。先保留旧完整路径，再增加 E/P 的明确消费路径；每个迁移入口都要证明强制约束没有消失。只做工程分类的入口先行，正式报告／资格路径在新发布链完整验收前仍使用旧完整锁。

历史版本、失败记录、未通过检查及缺失外部文件不因迁移重新命名为成功。工程作业可按 G2 用新 run id 重跑；最终 holdout 仍一次性。发布锁生成成功也不能代替产品硬审、main/CI 或 G4 的全量零新增。

## 6. 将来实施所需验收与未决项

实施计划至少应覆盖：

1. 同一冻结 S/I/T 的 E 可重复计算；任一成员／名单漂移、缺项、路径逃逸或别名都拒绝。新旧完整路径在未迁移范围行为一致。
2. E 可驱动已授权工程入口而无需伪造 R；E、错误类型／版本或范围不匹配的 P 均不能进入正式报告／资格消费。用途篡改、报告替换、假 PASS、开发者自审和证据遗漏的反例必须拒绝。
3. 新 P 真实序列化后经完整 verifier 及独立报告侧核验成功；循环引用、尚未终态日志、旧源码配新锁、旧报告配新 E 的反例失败。原 T7／输入 pins 的失败仍可原样复现。
4. 同段工程回放的正常数值及既有冻结产物不变；完整 BEFORE/AFTER 使用现有监督链与比较器，按用例新增 F/phase E/CE 为 0，无人口遗漏或新增 skip/xfail，不用新 E/P 刷新预期来掩盖失败。
5. 独立硬审无条件 PASS、接受源码 main、实际 HEAD CI 及新完整基线入库后，方能声明实现完成。计划意见只供作者处置，不设计划 PASS 门槛。

待后续实施计划／外部审核明确的事项仅有：首批工程入口的逐项白名单与用途字段 schema；E/P 和审核报告字段的具体兼容版本；语义认可 pins 的迁移名单、责任人与验证范围。建议首批限制为离线 profile 和已授权 SYNTHETIC 工程作业，未知入口保持原完整锁要求。本文不代替这些事项的有效实施裁定，不新增状态页。

本申请只做设计交付；未修改规则、源码、测试、旧 F/锁/报告，未执行冻结、full suite、研究或 profile。保持 `enable_trading=False / observer=hold / broker=NOT_RUN / real send=0 / real cancel=0`，凭据、holdout、服务、系统、UI 和模型配置均未触及。
