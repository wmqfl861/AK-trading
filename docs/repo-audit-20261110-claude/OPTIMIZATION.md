# AK-trading 优化方案（第四轮）

日期：2026-11-10 · 依据：[REVIEW.md](REVIEW.md) · 落地安排：[BLUEPRINT.md](BLUEPRINT.md)、[FIXES.md](FIXES.md)、[DEVELOPMENT-PLAN.md](DEVELOPMENT-PLAN.md)

> 这是讨论稿。你说过看完功能说明后再一起定优化方向，所以这里把每个方向的选项、代价和我的建议都写出来，需要你拍板的地方集中在最后一节的 J1–J8。在你决定之前，只有“不需要决定就该做”的第一批（见 BLUEPRINT 的阶段一）适合交给本地 agent。

## 我理解的你的需求

这个会话读不到之前对话里保存的项目记忆，以下来自仓库里的记录：

1. 主线是“正确的策略实现 → 可复现的历史回测 → 本地 paper 模拟”，螺纹钢优先，日线和分钟线各自出报告。
2. 你批准了 G1–G4：并行收窄、工程运行可重跑、取消秒级预算、一页状态页并以“合入 main 且 CI 通过”为完成标准。
3. 不开真实交易，不让 agent 碰凭据；仓库可见性、防火墙、数据库角色、客户端界面只由你操作。
4. 你希望看到的是策略研究的实际产出，而不是更多过程记录。

如果有仓库里没写的需求（比如资金规模、想先做哪个品种、对 v1 和 v2 的偏好），讨论时告诉我，方案会跟着改。

## 方案的出发点

前三轮的建议集中在速度和流程上。这一轮的发现改变了排序：

| 排序 | 问题 | 为什么排在这里 |
| --- | --- | --- |
| 1 | v2 的策略在真实时钟和日历下开不出仓（X01、X02） | 不修这个，后面跑得再快、流程再顺，得到的都是零成交 |
| 2 | 没有全量回归的对照（X20、Y03） | X01 就是这样漏过去的；不补上，下一次修复还会带进新的问题 |
| 3 | 昂贵的运行在开始前没有可达性检查（X03、X04、X05、Y01） | 几天的计算可能在第一行就注定没有结果 |
| 4 | 分钟线的速度（X10、X11、X12） | 真实瓶颈，但要在 1–3 之后做才有意义 |
| 5 | 仓库自足、流程、安全 | 持续性的成本，逐项收敛 |

## O1 先让策略能开仓

**现状**：TREND、BREAKOUT 在决策晚于收盘时永远凑不齐确认；日线在真实日历上所有策略都凑不齐；震荡三族永远过不了准入。

**方案**：

1. 修 X01 的两个现象和 X02，具体改法见 FIXES 的 K01、K02。三处都涉及语义，需要计划作者给出裁定，但裁定的范围很窄。
2. 给 M3B 加一组“真实形状”的测试夹具：决策时刻晚于收盘；日历带夜盘和多个交易节；状态由 `assess_regime` 生成而不是手工构造。以后凡是“某类策略能开仓”的测试，都要在这组夹具上也成立。
3. 加一个端到端的自然链冒烟测试并放进 CI：用小的合成数据走一遍 `build_strategy_context → evaluate → gate → choose`，断言每个应当能开仓的策略族至少出现一次 `OPEN`。它的作用是防止“每个零件都通过、合起来走不通”。

**代价**：K01、K02 的代码改动各自在几十行以内，但会改变 `strategies/registry.py`、`state.py`、`probability/regimes.py` 的哈希，需要新的合同锁。

**不建议的做法**：只改测试夹具让前瞻测试重新变绿，或者把决策时刻强行对齐到收盘时刻。真实行情的可用时刻总是晚于收盘。

## O2 昂贵运行之前先做可达性预检

**现状**：H7 计划跑 72 个单元格；H8 的一个作业给了 72 小时。这些运行在开始前，没有人算过“在这份配置下，有没有可能出现一笔成交”。

**方案**：加一个只读的预检脚本，在任何 walk-forward 或 profile 运行之前执行，几秒钟出结果，写进报告的第一节：

| 检查 | 算什么 | 不通过时 |
| --- | --- | --- |
| 资金 | 每个“品种 × 频率 × 策略族”开 1 手所需的最低权益，对照配置里的初始资金 | 标出哪些单元格必然 `BUDGET_INFEASIBLE` |
| 样本 | 每个证据单元在校准窗口内能达到的样本数上限，对照 200 / 500 | 标出哪些策略族必然证据不足 |
| 收益回合 | 训练窗口内每个策略最多能有多少个回合，对照 200 | 同上 |
| 日历 | 输入包里交易节的证据状态、K 线的状态和可用时刻 | `synthetic=false` 时指出会在哪一行退出 |
| 确认 | 观察期到期时刻与第 n 次观察时刻的先后 | 指出哪些策略族凑不齐确认 |

预检不改变任何门槛，只把“结果已定”的情况提前说出来。`probes/budget_feasibility.py` 是其中资金一项的雏形。

**代价**：一个约 300 行的脚本加测试，不触碰产品代码。

## O3 日线这条线怎么走（需要你决定）

修好 O1 之后，日线仍然面对样本量和资金两道门槛。三个选项：

| 选项 | 做法 | 多久能看到结果 | 能回答什么 | 代价 |
| --- | --- | --- | --- | --- |
| **A. 先用 v1 出日线基线报告（建议）** | 用现成的 v1 四个策略和回测引擎，在 RB 上做样本外的滚动检验，加资金和保证金敏感性；跑通后扩到 M、I | 1 到 2 周 | 最朴素的趋势、回归规则在样本外有没有正的期望；资金多大才做得动 | v1 没有概率门控，手续费和保证金是假设值；结论是“基线”，不是 v2 的资格认定 |
| B. 修好缺陷后按原规格跑 v2 的 H7 | 不改门槛，不改窗口 | 3 到 4 周 | 工程链路在真实数据上跑通 | 结果大概率仍是全部零成交（样本量、资金） |
| C. 给 v2 日线预先登记一套专用设计 | 运行之前由计划作者定好更长的校准窗口、同品种多合约合并计样本的方式；资金用 100 万元并报告最低权益 | 4 到 6 周 | v2 的概率门控在日线上有没有增益 | 需要更长的 RB 历史输入；是计划变更，要你批准；门槛改动必须在看到任何结果之前定死 |

我的建议是 **A 现在做，C 作为 v2 日线的正式路线，B 不做**。理由：

- A 用的代码已经存在并且跑出过结果，缺的只是样本外检验这一步。它最快给你一个关于策略本身的答案。
- A 的结果还能反过来回答 C 值不值得做：如果最朴素的趋势规则在样本外都是负的，v2 那套门控在日线上也很难找到可做的机会。
- B 花的时间和 C 差不多，却几乎确定得不到信息。

v1 和 v2 并存是第一轮就提过的架构问题（P2-1）。选 A 不等于放弃 v2：v1 在这里是对照基线，v2 的 FIXED 和 CASH 两种选择方式本来就是为了和简单规则比较。

## O4 分钟线提速

**现状**：见 REVIEW 的 X10–X13。

**方案**，按收益和风险排序：

1. **日历索引**（K10）。给 `v2/clock.py` 加一个按“交易节元组的身份 + 品种”缓存的索引：交易节只检查和排序一次，分钟格和交易日各存一个有序数组，查询用二分。对外函数的签名和返回值不变。探针已经证明等价，并且给出了参考实现。
2. **上下文共享**（K11）。`build_strategy_context` 里与策略无关的部分（品种交易节、可见 K 线、日线背景、截止时刻）按“合约 × 决策时刻 × 频率”算一次，七个策略共用。日线背景按“合约 × 来源日线”缓存，一个交易日内不重算。
3. **短日历多尺度 profile**（K12）。在 1、2 做完后，用 5、20、60 天三种长度各跑一次 cProfile，看剩下的时间花在哪、随长度怎么增长。代替现在 568 天的单次长跑。
4. **模型拟合向量化**（K13，需要你批准）。把梯度下降、树分裂、分位数回归改成 numpy 运算。等价标准要由计划作者先定：是要求逐字节相同（那就只能保留纯 Python 作为参考实现，numpy 版本只用于加速并在固定精度上比对），还是接受“数值在容差内相同、哈希随版本更新”。

**顺序上的理由**：1 和 2 不改变任何数值，风险低、收益大，应该先做；3 用来确认 4 是否还有必要；4 涉及依赖和等价标准，放在最后。

**不建议的做法**：继续沿用“每个热点函数单独立项、单独证明等价、单独审核”的方式。H4 证明了这种方式能做对，但它花了三天修一个函数，而同类的函数还有十几个。日历索引和上下文共享应当各作为一个整体来做。

## O5 回归保护

**现状**：CI 覆盖约 18%；全量测试自 10 月 26 日起没有在 HEAD 上跑过；验收标准不要求“没有新的失败”。

**方案**：

1. **失败清单对照**（K03）。在本机固定环境下跑一次全量，把失败和错误的测试编号存成一份基线文件入库。以后每次合入前后各跑一次，脚本比较两份清单：新增的失败必须为零，否则不算完成。基线里已有的失败不要求修，但不允许增加。这一条不依赖把全量变绿。
2. **CI 第二层**。在现有作业之外加一个装齐可选依赖的作业，跑 `tests/test_v2_m5*.py`、`tests/test_v2_forward*.py` 中不依赖本机工件的部分，以及 O1 的自然链冒烟测试。依赖本机工件的测试用统一的标记跳过并说明原因，而不是在收集阶段失败。
3. **验收标准补一句**：“全量失败清单相对合入前没有新增”。写进 G4。

**代价**：全量在你的机器上大约 20 分钟一次。

## O6 仓库自足

**现状**：见 REVIEW 的 X21、X22。

**方案**：

1. 把运行研究入口所需的小文件纳入跟踪：合同锁、研究配置、报告的 manifest。建议放在新的 `research/` 目录下，和被忽略的 `data/research_runs/` 分开。
2. 输入数据包不进公开仓库。仓库转私有之后，再决定用 Git LFS、私有的发布附件，还是只记录哈希和生成命令。
3. 数据管线：把缺的模块从本机的未跟踪目录移进 `src/ak_trading/datapipeline/` 并补上 `__init__.py`；如果它已经不再使用，就把仓库里那 7 个不完整的模块和对应测试移到归档目录。两者选一，不要维持现在的半截状态。
4. 候选代码每天推到远端分支。仓库转私有之后就没有理由只放在本机。

## O8 安全

全部只能由你本人执行，agent 只准备步骤：

1. 仓库转为私有。之后再决定要不要许可证。
2. 轮换行情服务的令牌；把 `docs/mcp-agent-guide.md` 里的公网地址换成占位符。Git 历史里仍然有旧地址，所以令牌必须换，入口最好改成 VPN 或 SSH 隧道。
3. 给执行服务或行情服务换一个默认端口，两者不再共用 17779。
4. 客户端策略的默认合约改成部署时必填，不再写死。
