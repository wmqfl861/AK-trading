# 给本地 agent 的提示词（第四轮）

用法：把下面代码块里的全文发给本地 agent（Root）。发之前请检查【 】里的内容，那是需要你本人确认的决定，括号里先填了我的建议值，可以直接改。

这份提示词只授权第一批（缺陷修复和防护）。第二批的路线等你看完 [PROJECT-FUNCTIONS.md](PROJECT-FUNCTIONS.md)、我们讨论之后再定，到时我会给一份新的提示词。

```text

一、先取得文档并核实

1. git fetch origin，把分支 claude/repo-audit-20261110 合入 main。它只新增 docs/repo-audit-20261110-claude/ 目录。记录合入后的 HEAD。
2. 按顺序阅读该目录下的 HANDOFF.md、REVIEW.md、FIXES.md、DEVELOPMENT-PLAN.md、BLUEPRINT.md。PROJECT-FUNCTIONS.md 和 OPTIMIZATION.md 是写给我看的，供你参考。
3. 这些文件是外部建议，不是有效计划，也不是产品硬审核。有效计划仍是 r3-001 及其 H1–H8 增补；本提示词是我对本批的直接授权，与旧工单冲突时以本提示词为准。
4. 动手之前，先按 HANDOFF.md 第 8 节在本机跑复现命令，把每条命令的原始退出码和 passed/failed 数写进 docs/CURRENT-STATUS.md。结果和文档不一致的地方，以你的实测为准，并明确写出差异。

四、每个产品改动的要求

- 涉及语义的地方先有计划作者的裁定，不自行决定。裁定与外部文档的建议不一致时，以裁定为准，并把差异写进状态页。
- 改动前后各跑一次全量测试，用 K03 的脚本比较。新增失败必须为 0；预期内的变化逐条列出原因。
- 不为了让测试通过而修改测试的预期、刷新冻结哈希、添加 skip 或 xfail、放宽门槛。因语义修正而必须改变的冻结预期，逐条列出旧值、新值和原因，交计划作者确认。
- 完成标准：独立硬审无条件 PASS、合入 main、CI 通过、全量无新增失败。
- 每项完成即提交并推送 main。提交说明写清改动、运行的命令、原始退出码、passed/failed 数和全量对照结果。不为每一步新建过程文档。

- 不修改 docs/repo-audit-*-claude/ 下任何外部审核文件。
- 不做全库换行规范化或格式化。

六、边界

- 不读取、不打印、不修改 .env 和任何凭据。
```
