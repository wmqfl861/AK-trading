## 新发现的问题

### N1 区间三族重复 bar 会提前开仓（P0，已复现）

`v2/strategies/reversion.py:84`、`grid.py:92`、`martingale.py:106` 都是 `confirmation = state.confirmation_count + 1 if gate.ok else 0`，没有 `d46274c` 给 TREND/PULLBACK 加的同 bar 判断。`range_entry_setup` 对同一根 bar 会原样返回 setup，但确认计数仍然加 1。

用项目自己的 SYNTHETIC 构造器复现（`entry_confirmation_bars=3`），三族结果完全一致：

| 送达顺序（bar 序号） | 实际结果 | 合同要求 |
| --- | --- | --- |
| 0、1、2，正常送达 | 第 3 根开仓，计数 3 | 符合 |
| 0、1、1，回穿 bar 重复送达 | 在重复的那一根开仓，计数 3 | 只能在第 3 根不同的 bar 开仓 |
| 0、0、0、1，建仓 bar 重复 3 次 | 第 2 根不同的 bar 就开仓，计数 4 | 同上 |

- **影响**：回放里的计时器事件和重启续跑都会重复送达同一根 bar，这正是 T7-A 审核在 TREND/PULLBACK 上判 FAIL 的情形。MARTINGALE 会分层加仓，提前开仓的后果最重。首批研究只用三个方向族，所以不阻断首批；但任何区间族进入研究或 paper 之前必须修好。
- **为什么现有测试没发现**：`test_v2_m3b_martingale.py::test_armed_and_recross_must_be_different_bars_no_double_count` 只检查了 `setup.consecutive_confirmations`，没检查真正决定开仓的 `state.confirmation_count`。
- **建议**：把“同一根 bar 不推进确认计数”抽成 `registry.py` 里的一个共享函数，全部入场族都调用它；再加一组对全部 7 个已注册策略参数化的重复送达测试，作为所有入场族的共同合同测试。这次 TREND/PULLBACK 的修复是两段复制的 11 行代码，共享函数能避免下一次漏改。探针见 [probes/test_range_duplicate_bar_probe.py](probes/test_range_duplicate_bar_probe.py)，可在仓库根目录原地运行。
- **候选修复已验证可行**（临时副本，未提交）：照 TREND 的写法给三族加同 bar 判断（`reversion.py` 还需从 `registry` 导入 `observation_bars`）后，探针 9 项全部通过；M3B 现有 212 项结果不变（209 通过、3 跳过）；v2 M1–M4 全部 858 项与修复前完全一致（839 通过、16 失败、3 跳过，失败项相同）。
- **实现时注意**：判断必须用上一状态的 `state.setup.last_bar_id`，不能用 `range_entry_setup` 刚返回的 setup，因为它在同一根 bar 时返回的就是旧 setup，在新 bar 时 `last_bar_id` 也总等于当前 bar。改动会改变这三个文件的哈希，涉及的冻结或接受清单要按原规则重新接受。

### N4 哈希钉住的是本机换行后的字节（P1，P1-9 的实证）

VERIFICATION 记录的 REPORT.md 哈希 `92065bb8…`（33,291 字节）是 Windows 签出时自动转成 CRLF 后的工作区字节。Git 里的同一文件是 32,939 字节，哈希 `49084029…`；我把它转成 CRLF 后正好得到 `92065bb8…`。

- **含义**：项目里大量“冻结哈希”取决于签出机器的 `core.autocrlf` 设置。同一个提交在另一台机器、CI 或新克隆里会被判为“漂移”。
- **建议**：加 `.gitattributes` 固定换行；冻结与接受清单改用 Git blob 哈希（`git hash-object`），或先规范为 LF 再计算；迁移时记录旧清单与新清单的对应关系。
